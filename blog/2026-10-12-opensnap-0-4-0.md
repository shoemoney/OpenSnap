# OpenSnap 0.4.0: the four things that almost went out wrong

*2026-10-12*

OpenSnap 0.4.0 shipped today: a native macOS 26 screen-capture and annotation app with a Liquid
Glass, icon-only interface, one-click upload to SFTP/FTP/WebDAV/S3, and full VoiceOver support. The
release itself was the boring part. The interesting part is the four places where the obvious move
was wrong, and what caught each one.

## 1. The force-push we didn't need

A history clean-up earlier in the week had rewritten the local repository to remove a private
screenshot that had slipped into the evidence folders. When it came time to publish, local `main`
and GitHub's `main` shared **zero commits**. `git merge-base` printed nothing; `git push` refused.

The obvious fix is `git push --force`. On a public repo that rewrites everyone's history and breaks
every link to a commit — and it would have been irreversible.

Before doing that we diffed one old commit against its rewritten twin at the raw-object level. The
only difference was a stripped SSH signature: same tree, same message, same dates. Then we checked
**all 178** commits GitHub had against their twins: 178 identical trees, 0 different. GitHub never
held the private file — it was added after the last push.

So instead of force-pushing, we replayed the 579 never-published commits (175 of them merges) on top
of GitHub's existing history, reusing each commit's exact tree, message and author. The final tree
was byte-identical to what had been reviewed, and the push was an ordinary fast-forward. Cost of
the measurement: one shell loop. What it avoided: rewriting public history for nothing.

## 2. The checker we loosened until it couldn't see

The visual acceptance run captures every screen in light, dark, Reduce Transparency and Increase
Contrast — 2,260 screenshots — and machine-checks contrast. A late regression made grey secondary
text on a selected row fall to **3.85:1** (the floor is 4.5:1), and the checker hadn't noticed,
because it never sampled text on selected fills.

We taught it to. It immediately threw **58 failures** — all false: PNG compression had turned the
desktop wallpaper's smooth gradient into flat bands that looked like selected rows. The quick fix
("a colour with several equally common neighbouring shades is wallpaper") made the run green.

The final review didn't trust a green run produced by loosening a check, and built the failure that
looked most like the false alarms: a real selected row at **3.3:1**, next to two sibling plates in
slightly different shades of the same accent. It passed. The loosening had also hidden real
selected controls. The rule was rewritten to judge each region's own structure (wallpaper bands
form a ramp inside the region; a selected row is flat and bounded), and that adversarial case now
lives in the checker's self-test, failing before the fix and caught after.

## 3. "29 announced, 0 pending" — wrong

The VoiceOver work keeps an inventory of every event a blind user needs to hear: capture started,
upload failed, link copied, Frame mode on. Mid-week the status line said 29 announced, 0 pending,
and that went into a progress update. The review found four rows still marked pending — countdown
cancelled, the two "Delete from Web" results, and the alert sheet itself. They were implemented (or,
for the alert, recorded as something VoiceOver already reads natively), and the true count became
**42 events: 38 announced, 1 native, 3 deliberately silent, 0 pending.** The earlier number stays
wrong in the record above; it is corrected here rather than quietly edited away.

## 4. The artwork that kept shipping

OpenSnap began as a rebuild inspired by Skitch. This week we removed every piece of the original's
art and sound and added a gate that fails if any of it is in the built app — by file name, by entry
in the compiled asset catalog, and by content hash, so a renamed copy is caught too.

Fresh clones passed. The long-lived local build failed with **65 original files** still inside it.
The build script created the bundle folder and copied new files in, but never removed files an older
build had put there. Every build now starts from an empty bundle, and the gate runs against the
real long-lived output, not only a clean clone.

## What shipped

- Four review rounds of the full gallery; the last ended in a sign-off with its conditions met:
  2,260 captures, 0 contrast failures, 0 advisories, 0 text-size violations.
- VoiceOver: 75 screens scripted ("what would it say"), zero open findings, and a live listening
  pass by the owner.
- A migration that copies — never moves — existing History, upload destinations and settings into
  the new app, verified on a copy of real data (58 of 58 drawings converted, originals untouched).
- Release: [v0.4.0](https://github.com/shoemoney/OpenSnap/releases/tag/v0.4.0), ad-hoc signed and
  not yet notarized.

The common thread: each near-miss was a green signal produced by the thing it was supposed to
check — a push that "needed" force, a checker loosened into silence, a count nobody re-derived, a
gate that only ever saw clean clones. The fix every time was the same: build the specific case
that would prove the green wrong, and run it.
